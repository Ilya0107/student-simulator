# Roadmap: улучшение архитектуры

Это план развития проекта, а не описание текущего состояния. Он составлен по итогам
ревью кода и описан по приоритетам: от безопасных улучшений к более крупным.
Текущий функционал игры меняться не должен — цель рефакторинга в том, чтобы сделать
код более читаемым, тестируемым и расширяемым.

## Текущие проблемы

| Проблема | Где | Почему это плохо |
|---|---|---|
| Логика перемешана с вводом-выводом | `player.cpp:129` (`exam`), `player.cpp:10` (`checkEnd`), `player.cpp:38`/`79` | модель сама печатает и читает `cin` → **нельзя протестировать** |
| «Божественная функция» `exam()` (~230 строк) | `player.cpp:129–363` | вложенные ветки, дублирование циклов ввода, тяжело менять |
| Магические числа | статы `main.cpp:203`, ежедневный `-20` `main.cpp:166`, пороги оценок `player.cpp:255–265`, подкуп `player.cpp:269,286`, гейты `player.cpp:140,162,207,245,313` | баланс нельзя менять в одном месте |
| Дублирование вывода эффектов | `main.cpp:26–68` (сон) и `main.cpp:121–163` (день) | одинаковый блок скопирован дважды |
| Пять копий цикла валидного ввода | `main.cpp`, `player.cpp:169,214,272,290` | копипаста, разные сообщения об ошибке |
| `using namespace std;` в заголовках | `player.h:7`, `text_data.h:3` | загрязняет пространство имён во всех включающих файлах |
| `<windows.h>` в модели | `player.h:3`, `color.h:3` | модель привязана к платформе, тяжёлые include |
| Глобальный `rand()/srand()` | `player.cpp:4`, `main.cpp:84` | результат невоспроизводим → нет тестов |

| Нет `namespace`, нет `enum class`, слабая `const`-корректность | везде | «учебный» стиль, низкая оценка ревьюера |

## Целевая архитектура

Принцип: **чистое ядро (без I/O) + данные + слой вывода + тонкая точка входа**.
Логику можно тестировать отдельно от консоли.

```
src/
├── core/                 # чистая логика, НИ ОДНОГО cout/cin
│   ├── types.h           # Effect, Choice, DayData, Dream, enum class Ending, ExamResult
│   ├── balance.h         # ВСЕ константы (constexpr): статы, пороги, цены, шансы
│   ├── player.h/.cpp     # модель: applyEffect, isAlive() вместо checkEnd() с выводом
│   ├── exam.h/.cpp       # правила экзамена -> ExamResult{grade, Ending} (без I/O)
│   └── game.h/.cpp       # цикл дней, сны, состояние (без I/O)
├── data/
│   └── content.h/.cpp    # DAYS, DREAMS, тексты (бывш. text_data)
├── io/
│   ├── console.h/.cpp    # цвет (бывш. color), enum class ConsoleColor
│   ├── input.h/.cpp      # readChoice(min,max) — единый валидатор
│   ├── view.h/.cpp       # рендер: статы, зачётки, эффекты, сны, концовки
│   └── app.h/.cpp        # оркестратор: game + view + input (бывш. тело main)
├── rng.h/.cpp            # Rng (интерфейс) + StdRng (<random>) + FakeRng (для тестов)
└── main.cpp              # 5 строк: init консоли + App().run()
```

### Ключевые решения

- **`enum class Ending`** и `struct ExamResult { int grade; Ending ending; }`:
  `exam.cpp` считает результат *чисто*, а слой `view` решает, какой текст и цвет показать.
- **Внедрение ГПСЧ**: интерфейс `Rng` с методом `uniform(a, b)`. В игре — `StdRng`
  (над `<random>`), в тестах — `FakeRng` с фиксированной последовательностью →
  детерминированные тесты.
- **Все константы в `balance.h`** (`constexpr`) — убираем магические числа.
- `std::array<Choice, 3>` и `std::array<DayData, 10>` вместо сырых массивов.
- Заголовки модели больше **не тянут `<windows.h>`**; `using namespace std;` убирается
  из заголовков.
- Убираем лишний `operator=`, добавляем пространства имён `sim::core` / `sim::io` / `sim::data`.

## Этапы

Сборка должна оставаться «зелёной» после каждого этапа.

### Этап 1 — чистка без изменения поведения
- Вынести константы в `balance.h`.
- `enum class`, `std::array`.
- Убрать `using namespace std;` из заголовков и лишний `operator=`.
- Единый `readChoice()` и единый `printEffect()` (убрать дублирование).
- **Проверка:** сборка без предупреждений + сравнение вывода игры (golden-транскрипт).

### Этап 2 — разделение логики и ввода-вывода
- Ввести `Ending` и `ExamResult`, вынести правила из `exam()` в `core/exam.cpp`.
- Перенести весь `cout/cin/setColor` в `io/view.cpp` и `io/input.cpp`.
- `core/game.cpp` управляет состоянием, `main.cpp` становится тонким.
- **Критерий:** игровой текст и поведение идентичны (диф транскриптов).

### Этап 3 — ГПСЧ и тесты
- `Rng` / `StdRng` / `FakeRng`; отдельный тест-проект в `tests/`.
- Тесты: пороги оценок, выбор концовок (смерть, бизнес, спорт, секрет, отчисление,
  4/3 с выгоранием и стрессом), исходы подкупа через `FakeRng`, эволюция шанса сна,
  ежедневный `-20`, границы `checkEnd`.
- CI: после сборки прогонять тесты.

### Этап 4 (опционально) — портируемость и конфиг
- Абстракция вывода (ANSI-цвета) для сборки вне Windows.
- Вынос баланса в конфиг (JSON/INI) и сохранения прогресса.

## Стратегия тестирования

- Чистые функции ядра (`exam`, `game`) тестируются без консоли.
- `FakeRng` делает случайные ветки детерминированными.
- Пограничные случаи: значения ровно на порогах (знания `65/75/85`, здоровье `30/80/91`,
  деньги `400/500/700/800`), нулевые и отрицательные характеристики.

## Критерий приёмки

Поведение и текст игры **не меняются**. Для контроля перед рефакторингом сохраняется
эталонный вывод (golden-транскрипт), который после каждого этапа сравнивается с новым.

## Риски

- Рефакторинг затрагивает почти все файлы → обязательна проверка через golden-транскрипт.
- Резервная копия исходного проекта хранится в отдельной папке.
